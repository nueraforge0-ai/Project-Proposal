### 3.7 System Development Methodology

#### 3.7.1 Development Approach

The system will be developed through iterative prototyping with Agile practices (Anifa et al., 2024). Working versions are built in short cycles and shown to representative users so that feedback from students, officers and administrators improves each version. This suits the project because the requirements for the gate workflow are better understood through use and discussion than through a fixed specification. Table 3.3 summarises the phases.

**Table 3.3: System development phases**

| **Phase** | **Main activities** | **Output** |
|----|----|----|
| Requirements analysis | Collect and analyse data on current handling; define functional and non-functional requirements for the three roles | Requirements specification |
| System design | Design the architecture, database, interfaces, role-based access rules, claim and release workflow and AI module | UML diagrams, entity relationship diagram, interface designs |
| Implementation | Build the web application and PWA features in iterations | Working prototype |
| Testing | Test functions, security, AI matching, usability and compatibility; correct faults | Test results and corrected prototype |
| Evaluation | Evaluate the prototype with students, officers and administrators | Evaluation results and recommendations |

#### 3.7.2 Requirements Analysis

Requirements will be drawn from the questionnaire, interviews, observation and document review, and from the scope in Chapter One. The main functional requirements are expected to include user registration and login, found-item registration by Security Officers with photographs, lost-item reporting by users, search of found items, claim submission, claim verification and release by officers, notifications, status tracking, account management and summary reports for administrators. The AI-related requirements are match suggestion, category suggestion and trend summaries, all presented as suggestions for human review. The non-functional requirements are security, privacy, usability on smartphones, reliability, and acceptable performance on limited connectivity.

#### 3.7.3 System Design

The design will use standard modelling techniques. Use case diagrams will show how the three roles interact with the system. Activity and sequence diagrams will describe the registration, matching, claim and release workflows. Data flow diagrams, a class diagram and an entity relationship diagram will describe the data and the database structure. Interfaces will be simple and responsive for smartphones. Chapter Four gives the preliminary requirements and design.

#### 3.7.4 Implementation Tools and Technologies

The prototype will be a responsive web application with progressive web application features, namely a web app manifest and a service worker, to support mobile access and intermittent connectivity (BrowserStack, 2026). The front end will use React, the server will use Node.js with Express, and the database will be MySQL. Visual Studio Code will be used for coding, draw.io for diagrams and Git for version control. The AI module will run on the server and call an external AI service for text similarity, category suggestion and summaries, with photograph-based matching added only if time allows. The final choice of tools may be adjusted with the supervisor.

#### 3.7.5 Security and Privacy Measures

Security and privacy will be built into the design. The system will require authentication and apply role-based access control (Rangappa, 2023), so that users see only their own reports and claims, officers see what their duties require, and administrators have a separate level of access. Passwords will be stored as salted hashes, input will be validated, database queries will use prepared statements, and uploaded files will be checked for type and size. Photographs will be stored outside publicly accessible folders and served only to authorised users. Public listings will show only a category and a general description. Names, contacts and identity numbers will be removed before any data is sent to an AI service, and the AI key will stay on the server. Access to claim and release records will be logged. Common web risks will be checked against the OWASP Top 10 (OWASP Foundation, 2021), and data protection follows Uganda (2019).
